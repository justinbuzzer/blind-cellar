# Blind Cellar

Private blind tasting, fairly scored. Every participant — including the host — privately registers their own bottle(s), everyone joins from their own phones and guesses blind, and once revealed the app scores everyone and shows a report with each bottle's contributor.

## Running it

1. Set up Supabase — see [SUPABASE_SETUP.md](SUPABASE_SETUP.md) (create a project, run `supabase/schema.sql`, get your URL + anon key).
2. Copy `.env.example` to `.env.local` and fill in the two Supabase values.
3. Install and run:

```bash
npm install
npm run dev
```

Open [http://localhost:3000](http://localhost:3000). A host creates a tasting on one device; everyone — including the host — registers their own bottle(s) from their own phones, then joins the blind tasting via a shared link, QR code, or join code.

Other useful commands:

```bash
npm run build     # production build
npm run lint      # ESLint
npm run test      # unit tests (Vitest)
npx tsc --noEmit  # type-check
```

## What this app supports

A tasting session moves through three stages: **registration** → **collecting** → **revealed**.

- **Host setup**: the host enters a title, date, their own display name, and a required **tasting format** (see "Tasting modes" below) — no wines up front. This creates the session and a normal participant record for the host — the host is a participant like anyone else, and appears exactly once in the leaderboard.
- **Registration**: the host gets a management link (`/host/[publicId]?token=...`) with a QR code, join link/code, live bottle count, and a "Start tasting" action. Every participant — including the host, via "Register my bottle" — can privately register any number of bottles using controlled dropdowns for country and region (region filtered by country), a grape/blend selector for single variety **or a structured multi-select blend picker** (see "Structured grape/blend" below), a year picker or NV toggle for vintage, a required **wine style** (Bubbles/White/Red/Sweet/Other), and free-text producer/wine-cuvée/optional private note. Each bottle gets a permanent, sequential anonymous number (`Bottle 1`, `Bottle 2`, …) the moment it's registered; numbers are never reused, even after a delete. The host can also arrange a separate **tasting order** for the bottles (see "Bottle number vs. tasting order" below) from a "Tasting order" panel on the host page, using Move up/down controls; this locks the moment tasting starts. Participants can edit or delete only their own bottles, and only during registration. No one — including the host — can see another contributor's bottle details or identity at this stage; the host sees only each bottle's anonymous number, wine style, and tasting-order position, never country/region/producer/vintage/notes or who contributed it.
- **Collecting**: the host starts tasting once at least one bottle is registered; this locks bottle registration, numbering, and the tasting order. What happens next depends on the session's **tasting mode** — see "Tasting modes" below.
- **Revealed**: whether reached via full blind's one-shot reveal, course-by-course's final bottle, or seen's "End tasting" action, the shared report unlocks for everyone in real time. For full blind and course-by-course, the report shows each bottle's full answer key, its **wine style** and **served position** (e.g. "Style: Red · Served 1st"), **and its contributor's name**, alongside Wine of the Night, Best Taster, Most Divisive Wine (with tie handling), per-bottle guess breakdowns (core vs. bonus categories), and the taster leaderboard. Seen tasting's report is rating-only instead — see "Seen tasting" below.
- **Scoring** is a 120-point-per-wine model: a 100-point **core** score (country 20, region 30, grape/blend 30, vintage 20 — exact, case/whitespace/accent-lenient matching) plus a 20-point **bonus** score (producer 10, wine/cuvée 10, exact normalised match). Price band is never scored, and no points are awarded or deducted for contributing a bottle. The leaderboard ranks by total points, then core points, then exact core-category matches, with ties sharing a rank. See "Scoring model" below for full details.
- A **"See a demo report"** link on the home page (`/demo`) renders a canned 3-bottle, 3-taster report (including contributor names) entirely client-side, for a quick look without creating a real tasting. It's explicitly labeled as a local-only demo and isn't saved anywhere.

## Tasting modes

Chosen once by the host when creating a session (`tasting_sessions.tasting_mode`) and **never editable afterwards**. Every session created before this feature existed safely reads as `full_blind` — today's only behaviour.

### Full blind tasting (default)

> All bottles are tasted blind before any wines are revealed. Best for comparative tastings where complete objectivity matters.

The existing, original flow: every participant (including the host and a bottle's own contributor) guesses every bottle **in the host's tasting order** (progress shown as e.g. `Bottle 4 — 1 of 5`) at their own pace via Previous/Next, autosaved as they go. No bottle's answer key, contributor identity, other guesses, or score is visible to anyone until the host performs one final reveal — there is no per-bottle reveal control in this mode. The host control page shows "All bottles remain hidden until the final reveal." during collecting.

### Course-by-course reveal

> Each bottle is tasted blind, then revealed before moving to the next. Best for casual dinners and relaxed tasting discussions.

Only one **active bottle** is open at a time — the earliest bottle by tasting order that the host hasn't yet revealed:

- Participants can only see and guess the active bottle (`/session/[publicId]/active`) — never an upcoming one's identity, guesses, or scores.
- A participant finalises their guess by tapping **Lock in my guess** (requires a rating, same as full blind's final-submission bar); the form then shows *"Your guess for Bottle [number] is locked. Waiting for the host to reveal it."* Unlike full blind, this locks per-bottle, not the whole session.
- The host doesn't need everyone to submit — **Reveal Bottle [number]** is available at any time, with a confirmation warning that anyone who hasn't submitted gets no score for that bottle (no guess is fabricated on their behalf). The host also sees a live aggregate `N of M participants submitted` count for the active bottle only, never individual guesses.
- Revealing shows a focused per-bottle screen (`/session/[publicId]/bottle/[wineId]/reveal`): full answer key, contributor, group rating stats, and every participant's guess/score breakdown for *that bottle only* — reusing the exact same scoring functions the final report uses, just scoped to one wine. There is deliberately no running leaderboard here, to keep a mid-tasting screen simple.
- A participant chooses **Continue to next bottle** whenever they're ready (never force-navigated away from a reveal they're still reading); reloading or returning later routes them to whatever's now current — the next active bottle, or final results if the session finished revealing while they were away.
- The host cannot skip a bottle, reveal out of order, reveal the same bottle twice, or reveal the whole session in one step — only the current active bottle, one at a time. Revealing the last bottle transitions the session straight to `revealed` and the normal final report.
- Bottle numbers and tasting order are never touched by any of this — only a new `wines.revealed_at` timestamp (null = not yet revealed) and a new `wine_guesses.locked_at` timestamp (null = still an editable draft) change.

### Seen tasting

> All bottles are visible from the start. Best for relaxed tastings where guests want to compare wines openly and rate them at their own pace.

A tasting-note-and-rating format, not a blind-identification competition — there is no guessing, no scoring, and no Best Taster:

- The moment the host starts tasting, **every bottle's full details become visible to every participant** — style, country, region, grape/blend, vintage, producer, wine/cuvée, and contributor name — at `/session/[publicId]/seen`. Bottle registration's usual pre-start secrecy (no contributor sees another's bottle) is unaffected; visibility only opens up once collecting begins.
- Participants **rate any bottle in any order** — tasting order is display order only, not a pacing restriction — and can **revisit and change a saved rating as many times as they like** while the session stays `collecting`. There is no per-bottle lock and no session-wide "submitted" state; a rating is simply the latest value saved for that `(guest, bottle)` pair.
- All individual ratings (and optional notes) stay private between participants during collecting — the host sees only aggregate progress (`N of M participants have rated at least one bottle`, `N of M possible ratings entered`), never anyone's individual rating.
- The host ends the tasting with **End tasting and reveal ratings**, which locks every rating (further save attempts are rejected server-side) and reveals a rating-focused report: Wine of the Night and Most Divisive Wine by average rating, a full bottle ranking (average → lower spread → more ratings → shared tie), and — expandable per bottle — every participant's rating (`No rating` shown honestly for anyone who skipped a bottle, never a fabricated zero).
- A seen rating is stored in the same `wine_guesses` table as full_blind/course_reveal guesses, but only ever sets `rating`/`confidence`/`tasting_note` — every identification-guess column simply keeps its existing blank default, exactly as an untouched draft guess already does in the other two modes. See `upsert_seen_rating` in `supabase/schema.sql`.

## Scoring model

**Every session is permanently tagged, at creation, with the scoring model it uses** (`tasting_sessions.scoring_version`) — chosen entirely server-side, never a client-supplied value, and never editable afterwards. Reports are still recalculated from live data on every load (there's no separate stored/frozen score row), but the calculation itself now branches on the session's own `scoring_version`, so revealing an old session always reproduces that session's original scoring rules, forever — never the current ones. Only two versions have ever actually existed:

- **`legacy_v1`** — every session created before this scoring-model replacement. Described below under "legacy_v1 (historic sessions)".
- **`core_v3_appellation_conditional`** — the current model, described below under "core_v3_appellation_conditional (current)". Every newly created session gets this version.

There is no intermediate version: an earlier plan to add a 140-point Appellation-bonus tier was never actually implemented (Appellation guesses existed but were always explicitly unscored), so `legacy_v1` is the only historic model that needs preserving.

### core_v3_appellation_conditional (current)

Five potential 20-point core categories, no bonus category at all:

| Category | Weight |
|---|---|
| Country | 20 |
| Region | 20 |
| Appellation | 20 — only when the actual wine has one recorded |
| Grape / blend | 20 |
| Vintage | 20 |

- **Conditional Appellation, conditional denominator.** If the actual revealed wine has a non-null Appellation, the possible score for that bottle is **100** (all five categories); if it doesn't, Appellation is excluded entirely — from the guess's field list, from the score, and from the denominator — and the possible score for that bottle is **80**. A participant is never penalised, and never scores an accidental correct, for a category that didn't exist for that particular wine — a blank Appellation guess against a wine with no Appellation is simply not part of the calculation, not a wrong answer.
- **Appellation correctness** is a plain exact-match comparison (same normalisation as every other field — trim, case-insensitive, accent/punctuation-lenient) between the guess and the actual Appellation, evaluated completely independently of Country/Region/Grape/Vintage — a correct Appellation call earns its 20 points even if every other field is wrong, and vice versa. No partial matches, no inference from other fields.
- **Producer and wine/cuvée are never scored** under this model — there is no bonus category. They remain optional guess fields, labelled `Producer, optional` / `Wine / cuvée, optional` in the guess form, and still appear in the reveal/report as a plain, unscored "Personal precision calls" comparison (`Guess: … / Wine: …`) if either side has a value — exactly the same non-scored comparison treatment `legacy_v1` already gave Appellation guesses.
- **Country, Region, Grape/blend, Vintage** use exactly the same comparison logic as `legacy_v1` (see below) — only the point values (20 instead of 20/20/30/20 — Region and Grape/blend dropped from 30 to 20) and the conditional Appellation category are new.
- **Ranking is by percentage, not raw points**, precisely because bottles can be scored out of either 80 or 100: `sum(points earned) / sum(possible points for the bottles this taster actually submitted a guess for) * 100`. A bottle the taster never guessed on is excluded from both sums, so someone who only tasted 80-point wines is never unfairly compared against someone who tasted 100-point wines. Ties break on: raw points earned, then number of submitted guesses, then count of exact core-category matches (the same final tie-break `legacy_v1` uses). The report displays both the percentage and the raw score in explanatory form (e.g. `284 / 360 points`).
- **Best Taster** is the taster ranked #1 by this same percentage-first ranking.

### legacy_v1 (historic sessions)

Frozen forever for every session created before this feature. Each guess earns a **core score (0–100)** and a **bonus score (0–20)**, for a **total (0–120)** per wine:

| Category | Weight | Type |
|---|---|---|
| Country | 20 | Core |
| Region | 30 | Core |
| Grape / blend | 30 | Core |
| Vintage | 20 | Core |
| Producer | 10 | Bonus |
| Wine / cuvée | 10 | Bonus |

- **Country, region, vintage** and **producer, wine/cuvée**: exact match after case/whitespace/accent/punctuation-lenient normalisation (`lib/normalize.ts`). No partial credit.
- **Grape / blend**: a **single variety** guess must exactly match the answer's canonical grape (aliases like Syrah/Shiraz, Pinot Gris/Pinot Grigio, and Zinfandel/Primitivo count as equal). A **blend** guess is tokenised on commas/slashes/semicolons/ampersands/hyphens, each token alias-canonicalised, and compared as an unordered set against the answer's blend — an exact set match is required, no partial-overlap credit. If the guess's mode (single/blend) doesn't match the answer's mode, it scores zero even if the text overlaps. If either side's mode is unknown (legacy data predating this field), scoring falls back to a plain alias-aware text comparison.
- **Vintage**: `NV` is an exact value, not a year — it only matches another `NV`, never a specific year.
- **Appellation guesses are never scored** under this model — see README "Region and Appellation" — "Blind-guess Appellation" for the unscored guess-vs-actual comparison shown in the reveal/report instead.
- **Confidence** is captured but never scored. **Price band** is never scored (and no longer collected in bottle/guess forms — see "Data model notes" below).
- The taster leaderboard ranks by **total points**, then core points, then count of exact core-category matches; a full tie on all three shares a rank — this ranking rule never changes for `legacy_v1` sessions, even after the ranking rule above was introduced for new sessions.

### Shared machinery

Both models share the same normalisation (`lib/normalize.ts`), the same grape/blend comparison engine (`lib/scoring.ts`'s `scoreGrapeBlend`, parameterised by point value), and the same curated Appellation map (`lib/appellations.ts`) — nothing about matching logic was duplicated between them, only the point weights, category list, and ranking rule differ. `lib/scoring.ts` keeps the two models' calculations in clearly separate, independently named functions (`scoreWineGuessLegacyV1` / `scoreWineGuessCoreV3`) behind one dispatcher (`scoreWineGuess`) that selects by the session's `scoringVersion` — never a shared, branchy implementation.

## Structured grape/blend

Choosing **Blend** replaces free-text entry with:

- **Grapes in this blend** — a multi-select of the same curated list single-variety mode uses (search box + checkboxes + removable chips), so blend components are canonical and score-comparable the same way a single variety is, regardless of typing/spelling/ordering differences between contributor and guesser.
- **Other grape(s), if not listed** — an optional free-text field for varieties not on the curated list (e.g. "Carignan, Counoise"). Multiple entries are split on commas/slashes/semicolons/ampersands/line breaks, trimmed, deduplicated case-insensitively, and alias-resolved to a curated grape's canonical name where recognised (so typing "Shiraz" here is the same as checking Syrah above) — a grape already picked from the curated list can't also sneak in via this field.

At least two total grapes (curated picks + unlisted entries, after the deduplication above) are required to save a blend on a bottle; one selected grape shows *"Select at least two grapes for a blend, or choose Single variety instead."* rather than saving. Guess entry stays lenient for autosave (a blank/incomplete draft is fine — see "Scoring model" above for why a blank guess just scores zero), but the same message blocks *final* submission if a guess's blend has exactly one grape, mirroring the existing missing-rating check.

Internally, the two curated/free-text inputs are combined into one canonical, alphabetised list (`lib/wineReferenceData.ts`'s `combineBlendComponents`) that becomes the "/"-joined display/storage text (e.g. `Cabernet Sauvignon / Merlot / Carignan`) — the same shape a blend has always been stored in, so scoring needed no changes (see "Scoring model" above). A new nullable `wines.grape_blend_components` / `wine_guesses.grape_blend_components` JSONB column separately stores which parts came from the curated multi-select vs. the free-text field (`{"selectedGrapes": [...], "otherGrapesText": "..."}`), purely so a blend can be re-opened for editing without losing that distinction — it is never used for scoring or display, and is never exposed to anon directly or through any pre-reveal view (only through the existing token-gated `get_registration_state`/`get_guest_session_state` RPCs, scoped to the caller's own bottles/guesses). A blend saved before this feature (no structured record) is re-parsed from its flattened text when its edit form loads — grapes matching the curated list get pre-checked, everything else lands in the free-text field verbatim — without ever needing to be re-saved.

## Other grape (single-variety custom entry)

**Single variety** mode's dropdown has one final option, **"Other grape"**, for a variety not on the curated list. Selecting it reveals a plain text input, labelled **"Grape variety"** with helper text **"Enter the grape variety."**, directly below the dropdown.

- **Available only for single-variety entry.** Blend mode already has its own unrelated free-text path ("Other grape(s), if not listed" — see "Structured grape/blend" above); this feature does not touch it, and a custom single grape can never masquerade as a blend or vice versa.
- **Stores the entered name in the existing grape value field — no new database column.** The typed text is saved directly as the bottle's/guess's canonical single-variety value (the same `grape_style`/`grape_style_guess` column every other single-variety grape already uses); the literal label "Other grape" is never itself persisted as a grape value. Which control to show (dropdown vs. text input) is tracked by an `otherGrapeSelected` flag that exists only in client/React form state — it is never sent to the server and never stored.
- **Does not create a separate stored sentinel/value.** Reopening a bottle or guess draft whose stored grape isn't on the curated list automatically re-selects "Other grape" and repopulates the text field with the stored value (`isCustomSingleGrape` in `lib/wineReferenceData.ts`, shared by every place that loads a record into editable form state) — nothing is silently blanked or nudged to the nearest curated grape.
- **Validation** (`lib/validation.ts`): required, trimmed, max 80 characters, letters (including accented Latin)/spaces/hyphens/apostrophes only. A comma/slash/ampersand/semicolon is rejected with *"Use Blend for more than one grape."* rather than the generic invalid message, so a contributor who types "Cabernet Sauvignon / Merlot" here is redirected to Blend mode instead of silently truncated or split. Guess entry stays lenient for autosave — a blank Other-grape draft is fine, same leniency as any other unset guess field — but a *non-blank, invalid* custom grape guess blocks final submission/lock, mirroring the existing incomplete-blend check.
- **Scoring uses the existing grape/blend comparison logic unchanged.** `scoreGrapeBlend` already falls back to plain alias-aware text comparison for any grape it doesn't recognise, so two matching custom grapes (e.g. both "Mondeuse Blanche") score correct exactly like a curated match, and two different or mismatched custom grapes score zero — no new "unknown grape" rule, no free credit, no scoring-model or point-weight changes.

## Data model notes: grape/blend, price band, and controlled country/region

- **Grape/blend** replaces the old free-text "grape/style" field everywhere in the UI. The underlying database column is still named `grape_style` (kept for migration safety — renaming a live column is riskier than mapping it internally); it now holds the canonical single-variety name or the flattened, alphabetised blend text (see "Structured grape/blend" above). A new nullable `grape_blend_mode` column (`'single' | 'blend' | null`) was added; `null` means the row predates this feature, and scoring/display fall back safely rather than guessing. See `lib/wineReferenceData.ts` for the curated grape list and alias table.
- **Price band** has been removed from all new bottle registration, guess entry, scoring, and results display. The `price_band`/`price_band_guess` database columns and any existing stored values are left in place untouched (the columns are simply no longer required or written) — nothing destructive happens to old data, it's just unused.
- **Country and region** are now controlled dropdowns (`lib/wineReferenceData.ts`), region filtered by the selected country. Both are stored as their canonical **display name** (e.g. `"France"`, `"Bordeaux"`) in the existing `country`/`region` text columns — deliberately *not* an ISO code — so a bottle registered before this feature (free-text country/region) and one registered after it remain directly comparable via the same text-normalisation matcher used everywhere else, with no separate code-to-name lookup needed for scoring or display. See the completion notes in `SUPABASE_SETUP.md` for the full rationale.
- **Wine style** (`wines.wine_style`) is a required, contributor-set classification (Bubbles/White/Red/Sweet/Other) — not scored or guessed, just a category shown to the contributor for their own bottles, to the host alongside the bottle's anonymous number only, and in revealed results. Existing bottles from before this feature backfill to `'other'`.
- **Bottle number vs. tasting order**: `bottle_number` (e.g. "Bottle 3") is the bottle's permanent anonymous identity — assigned once at registration from a monotonic per-session counter, and never reused or changed, even after a delete. `tasting_order` is a *separate*, mutable 1..N sequence the host can freely rearrange during registration (via Move up/down controls on the host page) to control the order bottles are actually poured and guessed in; it's contiguous and unique per session, defaults to registration order, is re-packed automatically when a bottle is deleted, and is frozen the moment the host starts tasting. A bottle keeps the same permanent number regardless of where it sits in the tasting order — e.g. "Bottle 3" might be tasted 1st.

## Region and Appellation

The single `Region / appellation` field has been split into two:

- **Region** — the same field as before, broad geographical region (e.g. Burgundy, Piedmont, Napa Valley), unchanged in meaning and still stored in the existing `region` column.
- **Appellation** — a new, optional, more specific recognised appellation within that region (e.g. Chablis within Burgundy), stored in a new nullable `appellation` column on `wines` and `cellar_bottles`.

**Curated, not comprehensive.** Appellation options come from a small, hand-picked v1 list in `lib/appellations.ts` — a deliberate design choice, not an oversight. Only ~30 country/region pairs are supported (see that file for the full list: most of France, Piedmont/Tuscany/Veneto/Sicily/Campania in Italy, Rioja/Ribera del Duero/Priorat/Rías Baixas/Jerez in Spain, Douro/Dão/Alentejo in Portugal, three regions each in Germany and Austria, California/Oregon/Washington in the US, four states in Australia, and three regions in New Zealand). Every other country/region combination simply has no Appellation field at all — this is expected, not a bug.

**Conditional visibility.** The field is hidden by default and only appears once both a supported country and region are selected (`hasAppellations(country, region)`); it always includes a blank "Select an appellation" option and is never required. Changing region (or country, which can also change region) always clears any selected appellation — a value chosen for Burgundy is never silently carried over to a different region.

**Adding a new supported region/appellation pair:** add the entry to `APPELLATIONS_BY_COUNTRY_REGION` in `lib/appellations.ts` (the region string must exactly match an existing `REGIONS_BY_COUNTRY` entry in `lib/wineReferenceData.ts` — add one there first if needed), then mirror the identical entry in the `is_valid_appellation` function's jsonb literal in `supabase/schema.sql`, since the server independently re-validates every appellation against its own copy of this list rather than trusting the client's dropdown (`register_bottle`, `update_bottle`, `add_cellar_bottle`, `update_cellar_bottle` all call it). Two region keys were deliberately adjusted from the most casual spelling to match this app's own existing region vocabulary — see the comment at the top of `lib/appellations.ts` for exactly which, and why.

**Not used for grape selection or blend behaviour.** Appellation never influences grape/blend auto-selection or filtering. Scoring involvement now depends entirely on which session it's in — see README "Scoring model": under `legacy_v1` (every session created before that feature), a participant's Appellation guess (see "Blind-guess Appellation" below) is never scored, purely an unscored guess-vs-actual comparison in the reveal/report. Under `core_v3_appellation_conditional` (current), the actual wine's Appellation set here is exactly what a guess is compared against for up to 20 scored points — conditionally excluded from the denominator entirely when this field is left blank on the actual wine.

**Privacy.** Appellation follows the exact same visibility rules as region/country: hidden in every pre-reveal view, masked the same way in `guest_visible_wines`, and only ever shown once a session is revealed (or, for Seen tastings, once the tasting starts) — see "Tasting modes" above. It also never appears in Personal Cellar's `/cellar` views to anyone but the owner, same as every other cellar field.

**Historic records are not backfilled.** Every bottle registered before this feature simply has a `null` appellation forever — there is no attempt to guess or infer one, and forms edit such a bottle exactly as before, just with the Appellation field starting blank (and hidden, if the bottle's country/region pair happens to have no curated list).

**Display.** Where wine identity is already shown as separate structured fields (the course-reveal per-bottle reveal screen), Appellation appears as its own row, hidden entirely when null — never a fabricated "Not specified". Everywhere else (tasting report rankings, the wine ledger, the cellar list), a concise `Appellation, Region, Country` string is used instead (`compactWineLocationLabel` in `lib/appellations.ts`), omitting missing values and never duplicating when region and appellation share the same display text (e.g. an unsplit "Champagne").

### Blind-guess Appellation

The same optional Appellation concept above is also offered on the participant's **blind guess**, in both Full-blind and course-reveal (the two modes share one guess-entry component, `components/WineGuessForm.tsx`) — Seen tasting has no blind guesses, so it is untouched.

- **Same curated map, zero duplication.** The guess field reuses `getAppellations`/`hasAppellations` from `lib/appellations.ts` and the server reuses `is_valid_appellation()` verbatim — there is no second list. It follows the identical conditional-visibility and reset rules as the actual-wine field above: hidden until a supported country guess and region guess are both chosen, and clearing/changing the region guess always clears the appellation guess (with an accessible "Appellation cleared because the region changed." announcement), while changing the grape/vintage/producer/wine/rating/note fields never touches it.
- **Scoring depends on the session's scoring version — see README "Scoring model".** The guess is always stored the same way (`wine_guesses.appellation_guess`, additive/nullable), but what happens to it at reveal time now differs: under `legacy_v1` sessions (every session created before the scoring-model replacement), it remains a plain, permanent passthrough — `ScoredGuess.appellationGuess`, never a `FieldScore`, never affecting `corePoints`/`bonusPoints`/`totalPoints`, no correctness computed. Under `core_v3_appellation_conditional` sessions (current), it is instead a genuine scored core category worth up to 20 points, conditionally excluded from the denominator when the actual wine has no recorded Appellation — see "Scoring model" for the exact rules. This is not a retroactive change: which behaviour applies is fixed forever by whichever version the session was created with.
- **Reveal display.** Under `legacy_v1`, an unscored `Appellation` comparison block appears in the per-guest breakdown (`WineResultCard`'s exported `AppellationComparison`, reused by the course-reveal per-bottle page) only if either the guess or the actual appellation is non-empty — a plain two-value "Guess: … / Wine: …" comparison, with no correct/incorrect label, no color coding, and no points. Under `core_v3_appellation_conditional`, Appellation instead appears as an ordinary scored row in the Core categories table (or "Not applicable" when the actual wine has none) — see "Scoring model". (The task spec that introduced this feature used example copy "Your call:" — this app has no existing concept of "which guess is the current viewer's own" anywhere in its post-reveal report, which is shared identically among all participants, so "Guess:" was used instead to avoid mislabeling someone else's guess as the viewer's.)
- **Privacy.** Follows the exact same pre-reveal secrecy as every other guess field — never exposed to other participants or the host before reveal, never validated against a second, looser rule than the actual-wine field, no RLS changes.
- **Historic guesses are not backfilled** — every guess submitted before this feature simply has a `null` appellation guess forever.

## Multi-device architecture

Sessions live in Supabase Postgres. See [SUPABASE_SETUP.md](SUPABASE_SETUP.md) for the full setup, the bottle-numbering concurrency approach, and the security model (host/guest tokens, Row Level Security, and why there's no service-role key anywhere in this app). This is the model every tasting workflow uses regardless of whether anyone is signed in — see "Accounts" below for the separate, optional identity layer that sits alongside it. In short:

- The browser only keeps two things locally: the **host token** for tastings this device hosts, and the **guest token** for tastings this device has joined (`lib/deviceStorage.ts`) — the host's own participant token is stored in the same slot a regular guest's would be, so registration/tasting pages need no host-specific branching. Everything else — session, bottles, guesses — is fetched live from Supabase.
- Host-only mutations (create session, start tasting, reveal) go through Next.js Route Handlers (`app/api/host/*`), which validate the host token server-side.
- Participant actions (join, register/edit/delete a bottle, autosave a guess, final submit) call `SECURITY DEFINER` Postgres functions directly from the browser using the public anon key; the functions validate the guest token and bottle ownership inside Postgres.
- Supabase Realtime pushes live status/bottle-count/submission-count updates to the host and registration pages, and reveal transitions to the tasting/results pages.

## Tasting archive

A private, read-only `/archive` page lets a host see every tasting they've hosted ("Hosted by you") and a participant see every tasting they've joined ("Joined by you") from **this browser**, once each one is revealed. It is deliberately browser-linked, not account-linked — there's no sign-in in this app (see "Multi-device architecture" above), so "who can see this in their archive" is defined the same way every other permission in this app already is: possession of a valid host or guest token.

- **How it works**: `lib/deviceStorage.ts` already stores a host/guest token per session it creates/joins; it now also appends a tiny `{ publicId, role, lastSeenAt }` reference to a local index (`blindCellar.archiveRefs`) whenever a token is stored — no raw token is ever duplicated into this index, it only ever points back at the existing per-session token slot. The archive page reads that index, resolves each reference's token, and POSTs `{ publicId, role, token }` triples to `POST /api/archive/lookup`.
- **How access is validated**: that route calls the exact same `SECURITY DEFINER` RPCs every other host/guest action already uses — `get_host_session` for a host reference, `get_guest_session_state` for a participant one — so a stale or forged token is rejected by Postgres itself, the same as it would be anywhere else in the app. A reference only becomes a visible archive entry once its RPC call succeeds *and* the session's `status` is `revealed`; a valid token for a not-yet-revealed session is kept locally but simply produces no entry yet. If a session is reachable through both a host and a participant reference (the host is always also a guest in their own session), it's shown once, under "Hosted by you."
- **What it reuses, not duplicates**: Wine of the Night and blind-identification accuracy come from the same `buildTastingReport`/`buildSeenTastingReport` pipeline the results page uses (now shared via `lib/supabase/reportData.ts`), and "View report" opens the *existing* `/results/[publicId]` page — the archive adds a "FROM THE ARCHIVE" marker and a "Back to archive" link there, nothing else. It does not change who can open a results link; that has always been "anyone who knows the link, once revealed" (see "Security model, in plain English" in `SUPABASE_SETUP.md`) — the archive only changes *discovery* (which sessions a given browser is shown), never report access itself.
- **Browser/device limitation**: this is genuinely a "this browser only" feature. A tasting hosted or joined on one phone won't appear in the archive on another device, or after clearing site data. This remains true even for a signed-in user in this phase — see "Accounts" below: signing in does not yet reattach this browser's archive to anything. The archive page says so directly: *"Your archive is available on this browser. Account-based access and cross-device history may be added later."*
- **Removing a local archive reference**: since there's no server-side record of "this browser's archive" beyond the tokens it already holds, clearing that browser's site data/localStorage for this app (or just for the `blindCellar.archiveRefs` / `blindCellar.hostToken.*` / `blindCellar.guestToken.*` keys) removes it from that browser's archive — there's nothing to delete on the server, since the archive was never a server-side list in the first place.
- **Future path (not implemented)**: linking this archive concept to the account layer described below, so it can follow a person across devices instead of staying pinned to one browser, is tracked as a Phase 2 follow-up — see "Accounts" and "Recommended next features" below.

## Accounts

An **optional**, passwordless account layer sits alongside the host/guest token model above — see SUPABASE_SETUP.md "Setting up Supabase Auth (accounts)" for the Dashboard configuration. Nothing about hosting or joining a tasting requires signing in; this is purely a foundation for a future cross-device tasting record.

- **Sign-in method**: email one-time code (OTP) via `supabase.auth.signInWithOtp()` / `verifyOtp()` — no passwords, no social login, no magic link (see SUPABASE_SETUP.md for why OTP was chosen and how magic links could be enabled instead). `/account/sign-in` is a single page with two steps (enter email, then enter the 6-digit code); `/account` shows the signed-in email, an optional account-level display name, a link to the archive, and sign out.
- **What signing in does NOT do by itself**: it does not retroactively migrate, attach, or reveal any of this browser's *existing* host/guest-token tastings to the account — those stay exactly where they were, browser-linked. What signing in *does* enable going forward, and for explicit historic claims, is described in "Account-linked tasting records" below.
- **Identity model**: a `public.profiles` row (`id` referencing `auth.users(id)`, `email`, optional `display_name`) is created automatically the moment someone verifies their first sign-in code — see `handle_new_user()` in `supabase/schema.sql`. This is deliberately the *only* thing an account layer touches; no `wines`/`tasting_sessions`/`guests`/`wine_guesses` row is ever linked to `auth.users` in this phase, and no tasting RPC gained an `auth.uid()` check.
- **A signed-in browser still uses the exact same anonymous RPCs and views** (`join_tasting_session`, `register_bottle`, `upsert_wine_guess`, `guest_visible_wines`, …) that an anonymous one does — see "Security model, in plain English" in `SUPABASE_SETUP.md` for the grant change this required (`authenticated` needed the same narrow access `anon` already had, nothing more) so that signing in never breaks or changes tasting behaviour.
- **Session storage**: the browser Supabase client (`lib/supabase/client.ts`) now uses `@supabase/ssr`'s cookie-based session storage instead of plain `localStorage`, and a minimal `middleware.ts` refreshes that session cookie on navigation. This only affects the Auth session itself — host tokens, guest tokens, and the archive's local reference index are completely untouched and still stored exactly as before.
- **Account display name vs. tasting display name**: the optional name on `/account` (`profiles.display_name`) is entirely separate from the name a guest types when joining a specific tasting (`guests.display_name`) — saving one never touches the other, and an existing session's guest name is never silently replaced.
- **Sign-out** clears only the Supabase Auth session (cookies) — it never touches `blindCellar.hostToken.*`, `blindCellar.guestToken.*`, or `blindCellar.archiveRefs`, so anonymous host/guest access and the local archive keep working immediately afterward.

## Account-linked tasting records

Builds on "Accounts" and "Tasting archive" above: a signed-in user can keep a durable, cross-device record of the tastings they host or join, and can explicitly add eligible completed tastings from this browser's existing browser-linked archive to that record. **Account linkage never replaces host/guest token authorization** — it is a second, independent "does a durable association exist" record layered on top, purely for *discovery* (which sessions show up in your archive on a new device), not a new permission. Nothing about the existing report-access model, RLS on tasting tables, or token validation changes.

- **Data model**: `public.account_tasting_records` (`user_id`, `session_id`, `role` — `'host'` or `'participant'` — `participant_id`, `claim_source` — `'automatic'` or `'browser_claim'` — `claimed_at`, `created_at`). Enforced by two partial unique indexes (one host link per user/session; one participant link per user/session/participant) so retries can never duplicate a row. It never stores a host token, guest token, Auth token, OTP code, or any tasting content (wines, guesses, ratings, results) — see `supabase/schema.sql`.
- **RLS**: `select using (auth.uid() = user_id)` and nothing else — no insert, update, or delete policy at all, for any role, including the row's own owner. The only way a row is ever created is `claim_account_tasting_record(p_public_id, p_role, p_token, p_claim_source)`, a `SECURITY DEFINER` RPC granted to `authenticated` only. Like every other RPC in this file, it's directly reachable via the anon key regardless of who calls it, so it independently re-validates the actual host/guest token against the exact session every time — a signed-in user who merely *knows* a session id, with no valid token for it, always fails. See SUPABASE_SETUP.md for the exact policy/RPC text.
- **Automatic linking**: when a signed-in user creates a tasting (`app/api/host/create-session`) or joins one (`app/join/[publicId]/page.tsx`), the exact same anonymous host-token/guest-token flow runs completely unchanged, and a `claim_source = 'automatic'` record is added afterward as a best-effort side effect — using a *separate*, cookie-aware Supabase client (`lib/supabase/routeHandlerClient.ts`) only to learn "is anyone signed in," never in place of the anon-key client the tasting RPCs themselves already use. If that link fails (or nobody is signed in), the tasting/join itself is completely unaffected; a host only ever sees a subtle, dismissible "…could not yet be added to your account record" notice, and a joining guest sees nothing at all (join errors are never surfaced for this).
- **Historic claims**: on the original browser, a signed-in user can click "Add to my tasting record" on an eligible completed (`revealed`) session in the browser archive, or on its report page — both call the same `claim_source = 'browser_claim'` path, gated additionally on the session actually being `revealed` (checked inside the RPC itself, not just client-side). "Eligible" always means: signed in, this exact browser still holds a valid host or guest token for this exact session, and the account hasn't already claimed it in that role.
- **Why `claim_source` isn't itself a security boundary**: both automatic and historic linking go through the identical token-validation path; the label is metadata for the revealed-status check and future auditing, not a privilege distinction. What actually governs whether a link is *visible* in "Your record" is the linked session's current status, re-checked at read time on every load — so an automatically-linked, still-`collecting` session simply doesn't show up yet, with no separate cleanup step needed once it's later revealed.
- **Same-browser requirement for claims**: identical to the browser archive's own limitation — a claim can only ever be made from the browser that still holds the actual host/guest token, since that token is what the claim proves. There is no way to claim a session from a device that never held it.
- **Cross-device behavior**: `/archive` shows two tabs for a signed-in user — **Your record** (everything linked to the account: automatic + successfully claimed, read directly from `account_tasting_records` under RLS, filtered to currently-revealed sessions, deduped host-over-participant, sorted the same way the browser archive is) and **This browser** (the existing browser-linked list, now also showing a quiet "Add to my tasting record" action on eligible unlinked entries, or "Already in your record" / "Available on this browser only" otherwise). Signing in on a second device shows only "Your record" — that device's own "This browser" tab starts empty, exactly as it should.
- **Report access is unchanged**: opening a report from either tab reuses the exact same `/results/[publicId]` route and report components (`TastingReportView`/`SeenTastingReportView`) — see "Multi-device architecture" above for why that route has never required a token to view a *revealed* report. "Your record" only adds a `FROM YOUR RECORD` / "Back to your record" marker (`?from=account`), the same way the browser archive already adds `FROM THE ARCHIVE` / "Back to archive" (`?from=archive`) — a display-only marker, never an authorization check.
- **What this phase intentionally does not do**: no "claim everything at once" bulk action (every claim is validated individually); no account merging between two different signed-in identities; no way to un-link or delete a record; no migration of pre-existing browser sessions just because someone signs in later; no change to what an anonymous browser, with no account at all, can already do.

## Palate Profile

A private, account-linked `/profile` page ("Your palate") that helps a signed-in user understand their own tasting activity, blind-tasting performance, wine preferences, and full tasted-wines ledger — a personal cellar ledger, never a social profile, leaderboard, or gamified score screen. Builds entirely on "Account-linked tasting records" above: every figure comes from the signed-in user's own `account_tasting_records`, re-read and re-aggregated server-side on every load, never a separately stored or cached "profile stats" row.

- **Tasting scope toggle**: a persistent, per-user preference — `Blind tastings only` (default) or `Include Seen tastings` — that governs every tasting/rating summary on the page (At a glance, Your wine record, the Tasted Wines Ledger, Recent evenings). **Blind palate never changes with this toggle** — it is always built from Full blind and Course-by-course sessions only, because a Seen-tasting participant already knows each bottle's identity before rating it, so a Seen rating is valid preference data but never valid blind-identification data. This is enforced structurally, not just by convention: `computeBlindPalate` is always fed a separately-filtered observation set (`extractBlindObservations`), which drops every Seen-tasting observation unconditionally regardless of what the caller passes anywhere else.
- **Data source and authorization**: every profile query starts from `account_tasting_records` under its existing RLS (`auth.uid() = user_id`) — never browser-only unclaimed archive records, never a session merely present in local storage, never an unrevealed/registration/collecting session, never another user's records. A signed-in host who also participated in their own tasting is counted once, not twice: see "Duplicate handling" below.
- **Duplicate handling**: when a session has both a `role = 'host'` and a `role = 'participant'` link for the same user (the ordinary case for a host who also joined their own session, plus the rarer case of joining the same session twice under different names), `resolveSessionLinks` (`lib/profile.ts`) collapses them into one `SessionLink` — the session counts once toward attendance, appears once in Recent evenings, and its ratings/guesses always come from the linked *participant* guest row, never a second one. A host-only link (no separate participant record) still counts toward hosted activity, and its own ratings/guesses are recovered from the session's `host_guest_id` — see the new grant below — since the host's own guess entry uses that same guest row under the hood (see "Multi-device architecture").
- **New, narrow grant — `tasting_sessions.host_guest_id`**: added specifically so the profile can resolve a host's own guest row without trusting anything client-provided. This is *not* new privacy exposure: every guest id (host or otherwise) is already fully readable by anyone via the existing open `guests` grant (`id, session_id, display_name, ...`) — this only reveals *which already-public guest id* belongs to the host, for a session the caller already independently holds an `account_tasting_records` link to. This is a deliberate small widening of the asymmetry noted in "Account-linked tasting records" above (the archive's host-role entries omit accuracy for the same reason this grant didn't exist yet); the Palate Profile needed the real figure enough to justify the grant, the archive did not.
- **Scoring is never recomputed**: every session's report is built via the exact same `loadTastingReportData` → `buildTastingReport` / `buildSeenTastingReport` → `scoreWineGuess` pipeline the final-report page and archive already use (`lib/supabase/profileData.ts`), and each session's own stored `scoring_version` governs which model that call uses (see README "Scoring model"). The profile only reads back each user's own `ScoredGuess` out of that existing report — "Blind accuracy" and per-category accuracy come directly from `ScoredGuess.totalPoints`/`totalPossiblePoints`/`fieldScores`, safely blending `legacy_v1` and `core_v3_appellation_conditional` guesses because each guess already carries its own correct possible-points denominator. There is no bonus-category/hit-rate figure under the current model, so none is shown; Appellation accuracy is aggregated separately and only counts guesses where the actual wine had one recorded.
- **Best-effort unique-wine matching**: two observations are the same wine only if producer, wine/cuvée, vintage, region, *and* country all match after normalization (lowercase, trim, collapse whitespace, accent/punctuation-insensitive — reusing the existing `normalizeText`, the same matcher blind scoring already uses). A partial match (e.g. same producer and vintage but different region) is always treated as two separate wines, never merged — see `normalizeWineIdentityKey` in `lib/profile.ts`. Original recorded values are always preserved for display; the normalized key is used for aggregation only.
- **Sample thresholds for preference conclusions** (never shown as a false claim from too little data): "Highest rated" categories require at least 3 rated observations; "Familiar ground" (producers/wines) requires at least 2 observations; "Most revisited" requires at least 2 distinct tasting *sessions* (not just 2 observations, which could otherwise double-count a single evening); Blind palate's "strengths/developing areas" readout requires at least 10 total submitted blind calls *and* at least 5 eligible calls in a specific category before naming it a strength or developing area.
- **The Tasted Wines Ledger is paginated, filtered, and sorted entirely server-side** (`GET /api/profile/ledger`) — the browser never downloads more than one page. Filter option lists (countries, styles, formats, years present) are derived only from the same already-scoped rows, so a filter dropdown can never reveal a value that exists only in someone else's data. For this app's realistic per-user data volume, "server-side" here means the Route Handler loads this one user's own account-linked sessions (never global data) and paginates in memory before responding — see "Recommended next features" for the true database-level pagination this would need at a much larger personal scale.
- **Report links from the profile** (`?from=account`) reuse the exact same `/results/[publicId]` route, `FROM YOUR RECORD` banner, and report components as "Your record" in the archive — no separate report engine, no separate authorization rule.
- **Navigation**: "Your palate" appears in the signed-in home header, the account page, the archive page, and a *revealed* report's nav row only — never on bottle registration, live host controls, active blind-guess entry, or any pre-reveal screen.
- **What this phase intentionally does not implement**: public profiles or profile URLs, social follows/leaderboards/comparison between users, badges/streaks/ranks/achievements, AI-generated notes or recommendations, PDF export, wine-marketplace or external wine-API integration, un-linking a specific tasting from the profile, and true cursor-based database pagination for the ledger (see above).

## Personal Cellar

A private, account-owned inventory of physical bottles at `/cellar` ("My cellar"), with a safe way to pull one of them into a tasting's existing bottle-registration flow. Wholly separate from the anonymous host/guest token model: a cellar bottle belongs to exactly one `auth.users` row, is never readable by anyone else, and only ever becomes visible inside a tasting indirectly — as the already-anonymous `wines` row it was used to create.

- **Physical-bottle model**: one `cellar_bottles` row represents exactly one physical bottle — never a quantity integer, even after "Quantity" below. Three bottles of the same wine are three separate rows. There is no bulk/CSV import, barcode scanning, OCR, or photo capture in v1; adding a bottle is a short manual form reusing the exact same wine-identity fields and validation as tasting bottle registration (`WineIdentityInput`, shared by both forms — see `components/registration/WineIdentityFields.tsx`).
- **Quantity (add-only convenience, not a stock count)**: the "Add a bottle" form has a `Quantity` field (default 1, integer, 1–100) so registering several identical physical bottles — e.g. a case of six — doesn't require repeating the form six times. Entering a quantity greater than 1 creates that many separate `cellar_bottles` rows in a single atomic server-side operation (`add_cellar_bottle`'s `p_quantity` parameter, validated and clamped server-side regardless of what the client sends) — it never stores "6" as a count on one row. Each created row is independently reservable, returnable, and consumable from the moment it's created, exactly as if it had been added one at a time; reserving or consuming one of a batch never affects the others. Quantity only exists on the add form — it's never shown or editable on an existing bottle (editing a bottle always edits that one physical unit, and `update_cellar_bottle` has no quantity parameter at all), and it is never itself persisted anywhere as a field on `cellar_bottles`.
- **Status lifecycle**: `available` → `reserved` (selected for a tasting; not yet used or returned) → `consumed` (used; permanent, never reverts). `reserved` can also return to `available` if the bottle is removed from its tasting before that tasting begins. All three shapes are enforced by a single database check constraint (`cellar_bottles_status_shape`) — every write path produces exactly one of the three, never a partial/inconsistent combination.
- **No direct client mutation at all**: unlike `profiles`, `cellar_bottles` has *no* insert/update/delete RLS policy for any role — not even "owner may update their own row." Every mutation (add, edit, reserve, return, consume) goes through a `SECURITY DEFINER` RPC that independently re-validates `auth.uid()` and ownership, since (like every RPC in this file) it's reachable directly via the anon key regardless of who calls it. Reads are plain RLS (`auth.uid() = owner_user_id`) — the same direct-browser-query pattern "Your record" already uses.
- **Reservation happens only at successful registration, not at selection** — clicking a cellar bottle in the selector just sets local UI state; the actual `available → reserved` transition and the new `wines` row are created together, atomically, inside `register_bottle_from_cellar` only once the participant confirms "Use this bottle." Two concurrent attempts to use the same cellar bottle can't both succeed: the RPC takes a row lock (`select ... for update`) on the cellar bottle before checking its status, so a second concurrent call blocks until the first commits, then re-reads the now-`reserved` row and fails safely with the same generic message a plain "no longer available" failure would show (`cellar_bottle_unavailable` never distinguishes "not yours" from "already used" from "doesn't exist").
- **Returning a bottle reuses the existing pre-tasting bottle-removal path, not a new one**: the existing `delete_bottle` RPC (used by the registration page's "Delete" button, unchanged) was made cellar-aware — if the bottle being deleted has a `cellar_bottle_id`, it atomically restores that cellar bottle to `available` in the same transaction. This means the existing UI needed **zero changes** to correctly "return to cellar" when a contributor removes their own cellar-linked bottle before the tasting starts. A second RPC, `return_cellar_bottle_to_available`, covers the same action from `/cellar` itself (the Reserved tab's "Return to cellar" button) — authorized by `auth.uid()` + cellar ownership alone, with no guest token involved, since the signed-in owner may not be on the browser that holds one. Both paths are blocked once the session leaves `registration` status (i.e., once the tasting itself has started).
- **Consumption is a deliberate, explicit action** (`Mark bottle as consumed`, shown only to the cellar owner on their own Reserved entries), never automatic — a reservation existing is not proof a bottle was actually opened. It's only permitted once the linked session has reached `revealed` (this app's "completed" state), so a bottle can never be marked consumed while its tasting hasn't started or is still in progress.
- **Cellar provenance is invisible everywhere except the owner's own `/cellar` page**: `wines.cellar_bottle_id` has no `anon`/`authenticated` column grant, so the only way it's ever read is from inside a `SECURITY DEFINER` function that explicitly selects it. The host, other participants, blind-guess screens, and final reports see a cellar-sourced bottle exactly like a manually-registered one — same anonymous number, same reveal timing, same everything. Storage location and personal notes never leave `cellar_bottles` at all; they're never copied onto the `wines` row.
- **Registration integration**: signed-in participants with at least one `available` cellar bottle see a segmented "Add a new bottle" / "Add from my cellar" choice at the top of the existing add-bottle page, defaulting to the existing manual flow. Choosing a cellar bottle shows a read-only confirmation (wine identity, format, "this bottle will be reserved…") with "Use this bottle" / "Choose another bottle" / "Add a new bottle instead" — wine-identity fields are never re-editable after a cellar bottle is selected, to preserve provenance between the physical bottle and the tasting bottle it becomes. Signed-out visitors and signed-in users with an empty cellar see only the unchanged manual flow, with a small non-blocking note — never a blocked or confusing registration.
- **What this phase intentionally does not implement**: bottle price/purchase-price tracking, market valuations, external wine-API enrichment, AI recommendations, drink-window analytics, CSV/bulk import, barcode/OCR scanning, bottle photos, shared/household cellars, cellar deletion, editing a bottle's identity once it's reserved or consumed, and a full tasting-cancellation feature (this app has no session-cancellation status today — "return to cellar" is scoped to the existing pre-tasting `registration` window instead; see "Assumptions and design choices").

## Assumptions and design choices

- Price band is no longer part of any new form or scoring calculation (see "Data model notes" above); it was previously required on every bottle.
- Grape/blend is required on every bottle (single variety from the curated list, or a non-empty blend description); the private note remains optional.
- Country and region are required, controlled-vocabulary selections on every new bottle and are no longer free text.
- "Other / Unknown" is offered as a normal region option per relevant country rather than a separate free-text "other region" field — the curated list plus that catch-all option was judged sufficient without adding a second, harder-to-score input path.
- "Confidence" is captured per guess but does not affect scoring, as specified.
- No Supabase service-role key is used anywhere — every privileged operation is enforced by a `SECURITY DEFINER` Postgres function validating a token, which lets the whole app run on the public anon key.
- Host and guest tokens are bearer credentials with no expiry or revocation in this MVP.
- The host control page shows a link to the shared results page after reveal rather than re-rendering the full report inline a second time, and no longer shows any bottle answer-key content itself (previously it did, before other participants could contribute bottles — that's no longer safe to expose to the host).
- Kept the database column name `host_notes` (now used for any contributor's private note, not just the host's) to avoid a wider, riskier rename across the schema, views, and every layer that reads it.
- `entered_by_type` from the brief's suggested schema was left out: `wines.contributor_guest_id` plus `tasting_sessions.host_guest_id` already fully answer "who contributed this bottle, and is it the host" without a redundant column.
- Existing sessions from before this feature keep their original wine labels (e.g. `Wine A`) and are never retroactively given a host participant record; see "Migrating an existing project" in `SUPABASE_SETUP.md`.
- Tasting order uses Move up/down controls rather than drag-and-drop — with typically 3–8 bottles, a couple of taps covers any rearrangement, and this avoids adding a drag-and-drop dependency for marginal benefit.
- A new bottle always joins the tasting order at the end (after whatever the host has already arranged), never inserted mid-sequence automatically.
- Reordering during registration never touches `bottle_number` — only `tasting_order`. Reordering is blocked entirely once the tasting starts (registration closed).
- The blend multi-select is an always-visible, searchable checkbox list rather than a floating popover/combobox — this app has no existing popover primitive suited to an inline dropdown (`Modal.tsx` is a full-screen dialog), and a search-filtered checkbox list is equally accessible without adding a new UI-library dependency.
- The two-grapes-minimum for a blend counts curated picks and unlisted free-text entries *together*, after cross-deduplication — picking "Merlot" and also typing "Merlot" in the unlisted field still counts as one grape, not two, so it can't be used to bypass the minimum.
- `grape_blend_components` is a convenience for re-editing a blend faithfully (which parts were curated picks vs. free text); it is never the source of truth for scoring or display — the flattened `grape_style` text is, exactly as it already was before this feature.
- Guess entry blocks a blend guess with *exactly one* grape at final submission (not before, so autosave never nags mid-draft), matching how a missing rating is already handled; a completely blank blend guess is left alone since it already legitimately scores zero.
- Wine/cuvée guidance is shown as persistent helper text under the field on every device size, rather than a tooltip/info icon, since the app's existing `TextField` already had a `hint` slot wired up for exactly this (accessible via `aria-describedby`) and the copy is short enough not to meaningfully add to page density.
- Tasting mode is locked at creation with no edit path, as specified — changing formats mid-session would leave `revealed_at`/`locked_at` state in an ambiguous position, so this was intentionally out of scope rather than a partial implementation.
- A course_reveal guess is only ever counted as "submitted" for host-progress and reveal purposes once explicitly locked (a new per-guess `wine_guesses.locked_at`) — a rating saved by autosave but never locked in still shows as "no submission" if the host reveals first, matching the requirement that no guess/score is fabricated.
- `guest_visible_wines` and `revealed_wine_guesses` (the views full blind's results page already relies on) are completely unchanged by this feature. Course-by-course reveal reads exclusively through new, narrowly-scoped RPCs (`get_active_bottle_state`, `get_revealed_bottle`) that check `wines.revealed_at` themselves — this was chosen over adding `OR revealed_at is not null` conditions to the shared views, to avoid touching code every other results/registration path depends on.
- The host's "N of M participants submitted" count for the active bottle is refreshed by short polling (every 5s) rather than Supabase Realtime. Realtime's `postgres_changes` broadcasts a full row per RLS policy, independent of column-level grants — so a permissive RLS policy on `wine_guesses` (needed for any realtime signal to reach anon at all) would broadcast guess *content* (ratings, country/region guesses) to every participant in real time, not just a completion count. `wine_guesses` therefore still has no anon grant and no realtime publication membership, exactly as before this feature; only `wines`/`tasting_sessions` changes (already realtime-enabled, never read for their payload content — only used as a "something changed, refetch through a secure RPC" signal) drive live updates.
- A revealed bottle's reveal screen intentionally omits a running leaderboard/ranking (the spec explicitly calls this unnecessary complexity for a mid-tasting screen) — it shows only that bottle's own group stats and per-guest breakdown, reusing `calculateWineResults` scoped to one wine.
- Seen tasting reuses the existing `wine_guesses` table rather than a new `wine_ratings` table — a seen rating and a blind guess are both fundamentally "one row per `(guest, wine)`, with a rating," and the existing table already has every column a seen rating needs (`rating`, `confidence`, `tasting_note`) plus a unique `(guest_id, wine_id)` constraint. A separate table would have meant either duplicating that constraint/index/trigger setup or writing extra joins anywhere both kinds of rows needed to be queried together — for no isolation benefit, since `upsert_seen_rating`/`get_seen_tasting_state` are already mode-gated and never touch the identification-guess columns.
- Seen tasting's report is built by an entirely separate pure-function pipeline (`lib/seenResults.ts`, `SeenBottleResult`/`SeenTastingReport` types) rather than a branch inside `lib/results.ts`/`lib/scoring.ts` — a seen rating has no answer key to score against, so forcing it through `calculateWineResults`/`ScoredGuess` would mean fabricating fake core/bonus scores. The two pipelines share only the generic, scoring-agnostic tie-break helpers (`rankByDescendingKeys`/`maxBy`/`minBy`, now exported from `lib/results.ts`).
- Seen mode's host progress card intentionally has no per-guest "Submitted"/"In progress" status (unlike full_blind/course_reveal's participant list) — there's no meaningful binary state for "rated some but not all bottles," and showing one anyway risked implying more granularity than the aggregate-only requirement intends.
- Like course_reveal's per-active-bottle submission count, seen mode's aggregate rating progress is refreshed by short polling (every 5s) rather than Realtime, for the identical reason: `wine_guesses` has no anon grant or realtime publication membership, since Realtime broadcasts full rows regardless of column grants.
- A seen-tasting rating save is an explicit "Save rating" action, not silent autosave-as-you-type like full_blind/course_reveal's guess entry — the spec's rating-entry actions are `Save rating` / `Back to all bottles`, and an explicit save also makes the exact required confirmation copy ("Rating saved. You can change it until the tasting ends.") meaningful as a one-time event rather than a debounced status label.
- The Tasting Archive's local reference index (`blindCellar.archiveRefs`) is a new, minimal addition rather than reusing a scan of existing `blindCellar.hostToken.*`/`blindCellar.guestToken.*` keys directly — `localStorage` has no efficient prefix-query API, so an explicit small index avoids crawling every key in storage on every archive page load.
- The archive's per-item server response distinguishes "invalid" (token rejected, or a guest token that resolves to a different session than the local reference claimed) from "not_revealed" (a genuinely valid token for a session that just isn't finished yet), so the client can safely forget the first kind of reference and keep the second for later. This is safe to return only because it's always the token's own holder asking about their own reference — it's not a public-facing error message.
- Archive entries never come from a query like "all sessions with status = revealed" — every entry is the result of independently re-validating one locally-held token through the same RPC any other part of the app would use for it. A browser with no local references never triggers a lookup request at all.
- Wine of the Night and blind accuracy in the archive summary are computed from the full `buildTastingReport`/`buildSeenTastingReport` result for each session, the same as the results page — a lighter, partial recomputation was considered and rejected, since duplicating even part of the scoring/ranking logic risked the two surfaces disagreeing over time.
- `get_guest_session_state`'s returned session object gained three additive fields (`id`, `createdAt`, `participantCount`) purely for the archive's own use — no existing caller reads them, so this needed no migration, only a `CREATE OR REPLACE FUNCTION`.
- Email OTP was chosen over magic links because it needs no callback route and no `emailRedirectTo`/redirect-URL Dashboard configuration to function at all — the whole sign-in/verify round trip happens through two direct browser calls (`signInWithOtp`, `verifyOtp`), which is both simpler to implement correctly and has fewer places an open-redirect or misconfigured Site URL could go wrong. See SUPABASE_SETUP.md for how a magic-link flow could be added instead.
- Every existing `anon`-only grant/RPC-execute privilege in `supabase/schema.sql` was widened to `anon, authenticated` *together with* an explicit `revoke all ... from authenticated` on the same four tables `anon` already had revoked — done as one atomic change, not two, specifically because a project's default privileges typically grant `authenticated` broad access no one had a reason to revoke before Auth existed. Widening the grants alone (without also revoking the untouched defaults) would have left a latent path for a signed-in session to read columns like `host_token_hash` that RLS's row-level `using (true)` policies don't restrict.
- Signing in never adds an `auth.uid()` check to any tasting RPC, and no `wines`/`tasting_sessions`/`guests`/`wine_guesses` row references `auth.users` — this phase's account layer is additive and parallel to the token model, not a replacement for any part of it.
- Profile updates (the optional account display name) go straight through Postgres RLS from the browser (`profiles_update_own`, column-limited via `grant update (display_name)`) rather than a Route Handler — this matches how every other participant-owned write in this app already works, and needs no new server code.
- `/account` and `/account/sign-in` protect themselves client-side (check `getUser()`, redirect if absent) rather than via middleware-based route protection — this app has no server-rendered, auth-aware page anywhere, so adding one just for this would be a bigger, riskier change than the two lines of client-side redirect logic it replaces.
- The OTP entry is a single labelled text input (`inputMode="numeric"`, `autoComplete="one-time-code"`, native paste), not six separate digit boxes — this codebase has no existing multi-box input pattern, and a single input is simpler, has one error message instead of managing per-box focus/backspace/paste-splitting, and still gets the same browser/OS one-time-code autofill treatment.
- `claim_account_tasting_record` takes an unambiguous `(p_role, p_token)` pair rather than separate nullable host/guest token parameters — the caller always knows which credential it's presenting (every archive/report entry already carries its own resolved role), so there's no "what if both are provided" case to arbitrate, unlike a two-nullable-token design would have needed.
- The account archive's host-role entries never show a blind-accuracy figure, only participant-role ones do — deriving a host's own guest-row id client-side would need a new `host_guest_id` column grant on `tasting_sessions` purely to recover one summary number, which was judged not worth the extra grant surface. Participant-role accuracy needed no new grant, since `account_tasting_records.participant_id` already gives the guest id directly. This is a deliberate, minor asymmetry, not an oversight — see `resolveAccountRecord` in `lib/archive.ts`.
- `getSupabaseRouteHandlerClient()` (cookie-aware) is a new file, not a change to the existing `getSupabaseServerClient()` (plain anon key, no cookies) that every host-token route already uses — swapping the shared client would have been a much larger, riskier edit than adding one new file used only by the two call sites that actually need to know who's signed in.
- Automatic linking after a signed-in join is fire-and-forget with `keepalive: true`, not awaited before navigating — this matches the explicit requirement that account linking must never add latency or a failure path to joining a tasting.
- "Your record"'s default outer tab is itself (not "This browser"), even when empty, for a signed-in user — the "Your record is waiting" empty state is worth showing proactively rather than only on request, and "This browser" remains one click away either way.
- The Palate Profile's Tasting scope toggle (`profiles.include_seen_tastings`) reuses the exact same column-grant pattern as `profiles.display_name` (`profiles_update_own` RLS + a narrow `grant update`) rather than a Route Handler — a boolean toggle needs no server-side validation beyond "is it true or false," which the column type already enforces.
- `?scope=` on `/profile` is read once on load (if present and valid) and kept in sync via `router.replace` on every toggle, purely for a shareable/bookmarked view of your own profile — it is never treated as a source of truth for persistence (only the toggle handler writes to `profiles`), and it never carries anything beyond the two fixed scope values, so it can't be used to smuggle a different user's data into the page.
- Standout bottles and Most revisited are computed from individual wine *observations*, not deduplicated by wine identity — the same wine tasted at two different evenings correctly appears as two distinct standout-bottle candidates (each with its own date/session), while "Most revisited" separately groups by identity specifically to surface repeats. Building both from one unified, pre-deduplicated list was considered and rejected, since it would have made "tasted the same wine at two different dinners" indistinguishable from "tasted it twice at once."
- A host-only account link whose `host_guest_id` can't be resolved (should not happen in practice, since every session gets one at creation) still counts toward "Tastings attended" and "Recent evenings" but contributes zero bottle/rating/guess observations — hosting is activity in its own right, per the spec's "host-only records still count toward hosted tasting activity."
- The ledger's "Year tasted" filter is the year of the *tasting date*, not the vintage year — vintage is already reachable via search, and a "year tasted" filter answers a genuinely different question ("what did I taste in 2025") that vintage can't.
- `cellar_bottles.region`/`grape_blend`/`vintage` are `not null default ''`/`not null`, matching `wines`' own shape exactly, rather than the nullable columns a first sketch of this schema used — every add/edit RPC still requires them non-blank in practice (same validation as tasting bottle registration), so making them nullable at the column level would only have invited the two tables to drift apart over time for no real flexibility gained.
- `delete_bottle` was made cellar-aware (releasing a linked cellar bottle back to `available` in the same transaction) rather than adding a second "remove this cellar-linked bottle" button to the registration page — the existing Delete flow already does exactly the right thing, including its own authorization (guest-token → contributor match) and its own `registration`-status gate; duplicating that as a new cellar-specific control would have meant re-deriving the same rules in a second place.
- `return_cellar_bottle_to_available` deliberately takes no guest/host token at all — its entire authorization is `auth.uid()` plus `cellar_bottles.owner_user_id`, since it's invoked from `/cellar`, where the signed-in owner may well not be on the browser that holds that session's guest token. This is a different, independently-sufficient authorization chain from the token-based one, not a weaker substitute for it.
- Reservation/return/consumption RPCs use one generic error tag per outcome family (`cellar_bottle_unavailable` covers "not found," "not yours," and "already used" identically) — mirroring `claim_account_tasting_record`'s existing "never reveal which specific check failed" pattern, since a more specific error here could let a caller fish for whether a given cellar bottle id exists or is owned by someone else.
- There is no session-cancellation feature in this app (sessions only ever move `registration → collecting → revealed`), so "return to cellar" is scoped to the `registration` status rather than to a `cancelled` one — this is the existing pre-tasting bottle-removal window, not a new concept introduced for the cellar. If cancellation is ever added, its handler would need to run the same cellar-release step `delete_bottle` already does.
- The cellar selector loads the signed-in user's `available` bottles once (bounded to 300 rows) and filters/searches client-side over that already-owner-scoped, already-bounded set, rather than re-querying Postgres per keystroke — the same "small personal dataset" scaling boundary already documented for the Palate Profile's ledger, appropriate for a personal cellar's realistic size.
- Editing is only ever allowed on `available` bottles, enforced by `update_cellar_bottle`'s own `for update` + status check (never a client-side-only restriction) — reserved/consumed identity is treated as provenance, not a draft, once a physical bottle has been committed to a tasting.

## Recommended next features

- Un-linking a specific account-tasting-record association, and/or deleting the account itself, once there's a clear product need for either
- Claiming/merging across two different signed-in identities (e.g. two accounts for the same person) — deliberately out of scope for this phase, see "Account-linked tasting records"
- Token expiry/revocation and rate limiting on the participant RPC functions, including the archive lookup and account-claim routes
- Partial-credit scoring rules (e.g. close vintage, correct country but wrong region)
- Proper Postgres migrations instead of a single `schema.sql` for schema evolution
- An external wine-data API for country/region/grape lookups, if the curated static list ever feels limiting
- True cursor/offset database-level pagination for the Tasted Wines Ledger, once a user's account-linked history is large enough that in-memory pagination over their own sessions stops being cheap
- Un-linking a specific tasting from the Palate Profile independent of un-linking it from the archive entirely
- Cross-session blind-accuracy trends over time (e.g. "improving" vs. a single all-time figure), deliberately left out of this phase's Blind palate section to avoid implying statistical rigor a small personal sample doesn't support
- Cellar bottle price/purchase-price tracking, market valuations, or Wine-Searcher-style external enrichment
- Bulk/CSV cellar import, barcode scanning, or label OCR
- Bottle photos
- Shared/household cellars, or any cellar access for a second signed-in user
- A "replace this cellar bottle with a different one" swap flow for an already-reserved tasting bottle — deliberately deferred; today the only supported change before tasting begins is return-to-cellar followed by a fresh selection
- True tasting-session cancellation (with its own cellar-release step), if this app ever adds one

## Manual test checklist

Run this against a real Supabase project (see `SUPABASE_SETUP.md`) using multiple devices/browsers (or one device + incognito windows to simulate other participants):

1. **Host creates a registration-stage session.** Go to `/host/new`, fill in title/date/your display name, submit. You land on `/host/[publicId]?token=...` showing "Bottle registration open", the join code, QR code, and copy-link/copy-code buttons.
2. **Host contributes zero or multiple bottles.** From the host page, click "Register my bottle" to add one or more bottles via `/register/[publicId]`; confirm "Start tasting" stays disabled with 0 bottles and enables once at least 1 exists — and confirm the host can also legitimately contribute 0 bottles and still start tasting once someone else has registered one.
3. **Multiple participants join on different phones/browsers** via the QR code or join link, landing on `/register/[publicId]`.
4. **One participant adds several bottles** — confirm the registration home lists all of them with sequential numbers, and "Add another bottle" is offered after the first.
5. **Different participants add bottles at the same time** (fire two registrations within a second or two of each other from different devices) — confirm no two bottles in the session ever get the same number.
6. **Bottle numbers remain sequential and unique**, and **deleted numbers are not reused** — delete a middle-numbered bottle, then register a new one, and confirm the new bottle's number is higher than every number ever issued, not a reused gap.
7. **A participant cannot see another contributor's answer key** — inspect the registration home and network responses; only your own bottles' details should ever appear.
8. **Participants can edit/delete only their own bottles before tasting starts** — confirm attempting to edit/delete via a manipulated URL for someone else's bottle fails.
9. **Host starts tasting and locks registration** — confirm the confirmation modal text, that bottle registration closes, and that participants on `/register` automatically transition to `/tasting` via Realtime.
10. **Host submits guesses as a participant** via "Enter my guesses" on the host page, using the same guess-entry flow as anyone else, including guessing their own contributed bottle.
11. **Guests submit guesses** for every bottle, autosaving as they go, then submit and see the "locked" screen.
12. **Host reveals wines** via the confirmation modal on the host page.
13. **Contributors are visible only after reveal** — before reveal, no contributor name ever appears anywhere; after reveal, every bottle's card shows "Contributed by [name]".
14. **Host appears exactly once in the leaderboard**, with their own bottle (if any) scored identically to everyone else's — no bonus or penalty for contributing.
15. **Existing pre-feature sessions still load correctly** — a session created before this migration (status `collecting` or `revealed`, wines labeled `Wine A`/`Wine B`) continues to work end-to-end without a host participant record.
16. **Country/region controls work correctly** in both bottle registration and guess entry — region is disabled with a "Select country first" placeholder until a country is chosen, only shows that country's regions, and resets to blank if you change country after picking a region.

21. **Existing sessions with legacy grape/style and price-band data still load and score sensibly** — a bottle registered before this update (no `grape_blend_mode`) still displays its old grape/style text and scores against new-format guesses using the alias-aware text fallback described in "Scoring model" above.

### Tasting archive
